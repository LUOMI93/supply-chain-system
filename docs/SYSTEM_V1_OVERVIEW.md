> 文档日期：2026-07-15
>
> 代码基线：`codex/add-setup-docs` / `0d4f443`
>
> 生产地址：`https://www.zftech.space`
>
> 适用对象：后续开发者、测试人员、运维人员，以及 2.0 重构负责人

## 1. 文档目的

本文记录供应链系统 1.0 已经落地的业务模型、技术实现、部署方式、历史问题和已知限制，作为 2.0 重构前的事实基线。

阅读时需要区分三类内容：

- **当前实现**：已经存在于 1.0 代码或正式环境中的行为。
- **已知问题**：代码中仍存在的不一致、风险或维护成本。
- **2.0 建议**：重构方向，不代表 1.0 已经实现，也不要求全部一次完成。

2.0 设计应以本文和实际代码为准，再结合业务规模重新决策，避免沿用已经失效的早期架构判断。

## 2. 项目概述

系统服务于汽车配件供应链产品资料的集中维护和查询，主要解决以下问题：

- 不同供应商提供的产品表结构不一致，难以统一管理。
- 一个产品通常包含多个规格，每个规格有独立 SKU、价格、车型和 OE 码。
- 产品图片可能来自本地上传、Excel 内嵌图片或网络图片 URL。
- 管理人员需要维护完整采购信息，浏览人员只能查看授权范围和非敏感数据。
- 数据需要支持 Excel 批量导入、按供应商导出、服务器持久化和备份恢复。

1.0 是一个适合小团队、单服务器运行的全栈单体应用。它已经完成正式域名、HTTPS、登录、权限、产品和供应商管理、Excel 导入导出、图片持久化、备份恢复及基本安全加固，并通过了正式环境手工验收。

## 3. 核心业务概念

### 3.1 产品组

`ProductGroup` 表示一个可被用户识别的产品，是列表、搜索、图片和公共信息的主要聚合单位。

产品组包含：

- 唯一的产品组 SKU。
- 产品名称和供应商。
- 产品链接、重量、尺寸、包装信息、装箱数、备注。
- 是否进入公开目录的 `isPublic` 标记。
- 多条规格和多张图片。
- 创建人、更新人、版本号和软删除时间。

### 3.2 产品规格

`ProductSpec` 表示产品组下的一个具体规格。一个产品组至少应有一条规格，规格包含：

- 规格 SKU，同一产品组内唯一。
- 工厂编号。
- 产品规格描述。
- 拿货价格和销售价格。
- 适配车型和 OE 码。

价格目前使用字符串存储，而不是数据库数值类型。这是为了容纳“待定”“面议”“区间价”等供应商原始文本，但也意味着 1.0 不能可靠进行数值排序、汇总和价格计算。

### 3.3 产品图片

`ProductImage` 只保存文件公开路径、文件大小和排序号，图片实体保存在 `UPLOAD_DIR` 指定的持久化目录中。

数据库与文件系统是两套存储：数据库备份和上传目录备份缺一不可。

### 3.4 供应商可见范围

`UserSupplierVisibility` 是 viewer 用户和供应商之间的多对多授权关系。viewer 只看被授权供应商下的产品；授权列表为空时，应当看不到任何供应商数据，而不是默认看到全部。

admin 和 editor 在产品 API 中默认可见全部供应商数据。

### 3.5 公开目录与内部 viewer

这两个概念不能混淆：

- `/catalog` 和 `/api/catalog` 是无需登录的公开目录，只返回 `isPublic = true` 且未删除的产品。
- 登录后的 viewer 是内部受限用户，按供应商授权过滤，但当前产品查询不会再按 `isPublic` 过滤。

因此，`isPublic` 只控制公开目录，不等同于 viewer 权限。

| 层级 | 1.0 选型 | 用途 |

应用采用单体结构：页面、认证、API、数据库访问和文件处理都在同一个 Next.js 项目中。1.0 不包含独立后端服务、队列、Redis 或对象存储。

## 5. 总体架构

```text
浏览器
  |
  | HTTPS
  v
Nginx
  |-- TLS 终止
  |-- 请求体限制 250 MB
  |-- 反向代理到 127.0.0.1:3000
  v
Next.js / PM2
  |-- 页面与客户端交互
  |-- Auth.js 登录和 JWT 会话
  |-- App Router API
  |-- Pages Router /api/import
  |
  +--> Prisma --> SQLite: /var/lib/supply-chain/prod.db
  |
  +--> 文件系统: /var/lib/supply-chain/uploads
```

### 5.1 主要请求链路

登录后的普通业务请求：

1. Nginx 转发请求，并保留 Host、客户端 IP 和 HTTPS 协议头。
2. `src/proxy.ts` 读取 JWT，处理页面跳转和基础路由保护。
3. API 内部再次通过 `requireAuth()` 做身份和角色校验。
4. Prisma 读写 SQLite。
5. 图片通过 `/uploads/[...path]` Route Handler 从持久化目录返回。

Excel 导入是一个例外：它仍使用 Pages Router 的 `src/pages/api/import.ts`，由 formidable 解析大文件，并直接通过 `getToken()` 读取登录 cookie。

## 7. 数据模型

```text
User 1 --- 0..1 UserColumnPref
User 1 --- n AuditLog
User n --- n Supplier (通过 UserSupplierVisibility)
User 1 --- n ProductGroup (createdBy / updatedBy)

Supplier 1 --- n ProductGroup
ProductGroup 1 --- n ProductSpec
ProductGroup 1 --- n ProductImage
```

### 7.1 主要表

| 模型 | 关键约束 | 删除策略 |
| --- | --- | --- |
| `User` | `username` 唯一；角色为字符串 | 当前为物理删除 |
| `UserSupplierVisibility` | `(userId, supplierId)` 唯一 | 用户或供应商删除时级联 |
| `UserColumnPref` | 每用户一条 | 用户删除时级联 |
| `Supplier` | `name` 唯一 | API 物理删除，并删除关联产品记录 |
| `ProductGroup` | `sku` 唯一 | 默认软删除，写入 `deletedAt` |
| `ProductSpec` | `(groupId, sku)` 唯一 | 产品组删除时级联 |
| `ProductImage` | 按 `groupId` 关联 | 数据行可级联，物理文件需单独处理 |
| `AuditLog` | 按实体、用户、时间建立索引 | 当前没有归档和清理策略 |

### 7.2 数据设计中的重要决定

- 产品和规格分表，避免一个产品多规格时重复所有公共字段。
- 产品组使用软删除，重新导入同 SKU 时会恢复 `deletedAt = null`。
- 供应商当前使用物理删除，且删除供应商会同时删除其产品、规格和图片记录。
- `ProductGroup.version` 在编辑时递增，但目前没有用它做乐观锁或冲突检测。
- `mustChangePassword` 和 `isActive` 已进入模型，但 1.0 尚未形成完整的首次改密和账号启停流程。
- `factoryCode` 存在于规格模型中，但当前导入逻辑将“工厂编号”主要作为规格 SKU 的后备来源，并未稳定写入该字段。

## 8. 权限模型

### 8.1 设计目标

| 能力 | admin | editor | viewer | 未登录用户 |
| --- | --- | --- | --- | --- |
| 查看全部内部产品 | 是 | 是 | 否 | 否 |
| 按授权供应商查看 | 不受限 | 不受限 | 是 | 否 |
| 查看拿货价、供应商真名、产品链接、备注 | 是 | 是 | 否 | 否 |
| 产品新增、编辑、删除 | 是 | 是 | 否 | 否 |
| Excel 导入、导出 | 是 | 是 | 否 | 否 |
| 供应商新增、编辑、删除 | 是 | 业务目标为是 | 否 | 否 |
| 用户和权限管理 | 是 | 否 | 否 | 否 |
| 审计日志 | 是 | 否 | 否 | 否 |
| 公开产品目录 | 是 | 是 | 是 | 是 |

### 8.2 当前实现中的权限不一致

供应商 API 已允许 `admin` 和 `editor` 新增、编辑和删除，供应商页面自身也接受 editor；但是 `src/proxy.ts` 把 `/suppliers` 放在 admin 专属路径中，且页面多数操作按钮只在 `role === "admin"` 时显示。

这与已经确认的业务规则“editor 可以创建供应商并处理全部业务数据”不完全一致。2.0 重构前应先把这条规则写成权限测试，避免只改 API、页面或路由保护中的一层。

### 8.3 viewer 隐私处理

viewer 的产品查询会：

- 按 `UserSupplierVisibility` 过滤产品和供应商。
- 隐藏供应商对象、产品链接和备注。
- 将规格中的拿货价格置空。
- 在供应商筛选和统计中使用由 SKU 前缀生成的代号。
- 前端隐藏供应商、拿货价、产品链接和备注列，以及编辑、删除、导入、导出入口。

权限必须以后端过滤为准，前端隐藏按钮只能改善体验，不能作为安全边界。

## 9. 功能实现

### 9.1 登录与账号安全

- 使用用户名和密码登录，密码通过 bcrypt 哈希保存。
- 使用 JWT 会话，默认有效期 30 天。
- 生产环境启用安全 cookie，HTTPS 下 cookie 名会带安全前缀。
- 连续 5 次密码错误后锁定 15 分钟；登录成功后清零失败次数。
- 新建和重置密码至少 12 位，并且必须同时包含字母和数字。
- 禁止使用 `admin123`、`editor123`、`viewer123` 等演示或常见弱密码。
- 生产首个管理员通过 `pnpm db:init:prod` 创建，不运行开发 seed。

当前没有登录接口的 Nginx/API 限流、验证码、双因素认证和完整的首次登录强制改密页面。

### 9.2 产品浏览

- 每页默认 50 个产品组，API 最大允许每页 100 个。
- 支持按产品组 SKU、名称、供应商、规格 SKU、规格、车型和 OE 码搜索。
- 支持供应商筛选，并把搜索和供应商筛选同步到 URL 查询参数。
- 固定产品组 SKU 和图片列，表头 sticky，表格单容器滚动。
- 多规格产品默认显示前 3 条规格，可展开或收起全部规格。
- 支持图片灯箱查看。
- 支持默认、采购、销售、仓库四套列预设。
- viewer 使用更精简的产品目录视角。

### 9.3 产品维护

- admin/editor 可以创建和编辑产品组、规格和图片。
- SKU、产品名称、供应商为产品组必填项。
- 规格为空时，接口不会自动强制补一条；Excel 导入则要求每个产品组至少有规格 SKU 或工厂编号。
- 编辑时根据规格 ID 判断新增、更新和删除，并检查规格 ID 是否属于当前产品。
- 产品删除为批量软删除，不立即删除规格和图片。
- 单个产品最多 12 张图片，单张最大 10 MB。
- 支持 jpg/jpeg、png、gif、webp 和 bmp。

### 9.4 供应商维护

- 供应商名称唯一，联系方式和备注可选。
- 列表显示产品数量，并支持名称、联系方式、备注搜索。
- 删除供应商是高风险操作：会物理删除供应商及关联产品、规格和图片数据库记录。
- 当前删除流程没有同步清理所有对应图片文件，可能产生孤立文件。

### 9.5 用户与可见范围

- 只有 admin 可以创建、编辑和删除用户。
- 可设置 admin、editor、viewer 三种角色。
- 可为 viewer 分配可见供应商。
- 管理员不能修改自己的角色，也不能删除自己的账号。
- 重置密码会解除锁定并清零失败次数。
- 页面显示锁定、失败次数和密码更新时间。

1.0 尚未提供账号启用/停用操作；`isActive` 只在登录时生效。`mustChangePassword` 也只保存状态，没有登录后强制跳转逻辑。

### 9.6 仪表盘与审计日志

- 统计产品组、供应商、规格、图片和最近 7 天新增数量。
- admin 首页显示最近操作，审计日志页支持按动作和实体类型筛选。
- 产品、供应商、用户的主要写操作会写审计日志。

当前审计日志不是严格审计系统：

- 部分日志失败会被忽略，以免影响主业务；部分用户日志失败则可能影响请求。
- action 命名存在 `CREATE`、`UPDATE`、`CREATE_USER` 等不同格式。
- `ipAddress` 字段存在，但大多数写入没有采集 IP。
- 没有变更前后快照、请求 ID、归档和保留期限。

### 9.7 公开目录

- `/catalog` 无需登录。
- 只展示未删除且 `isPublic = true` 的产品。
- 返回产品组 SKU、名称、第一张图片和规格的销售价格、车型、OE 码。
- 不返回供应商、拿货价格、产品链接和备注。

当前公开目录 API 一次返回全部公开产品，没有服务端分页、限流或缓存。产品量增长后需要调整。

## 10. Excel 导入

Excel 导入是 1.0 最复杂、最需要保留回归样本的模块。

### 10.1 输入限制

- 前端接受 `.xlsx` 和 `.xls` 文件名。
- 服务端使用 ExcelJS 的 xlsx 读取器，真正的旧式二进制 `.xls` 不属于可靠支持范围；2.0 应明确只支持 `.xlsx`，或引入经过验证的 `.xls` 转换流程。
- formidable 文件上限为 200 MB。
- Next.js 代理请求体上限配置为 250 MB。
- 正式 Nginx 的 `client_max_body_size` 为 250 MB。
- 单次最多 5000 条非空数据行。
- 只读取第一个工作表。
- 在前 20 行中搜索同时包含“产品组SKU、产品名称、供应商”的表头；找不到时回退第 1 行。

大文件能否上传取决于浏览器、Nginx、Next.js 和 formidable 四层限制，不能只修改其中一处。

### 10.2 列名兼容

必填列为：

- 产品组 SKU。
- 产品名称。
- 供应商。

每个产品组还必须至少有一条规格 SKU；“工厂编号”可以作为规格 SKU 的后备值。

导入会去除表头空格，并兼容部分常见别名和错别字，例如“产品组编号”“产品名”“供货商”“规格编号”“厂编”“成本价”“售价”“车型”“OE编号”等。

这种模糊兼容解决了真实供应商表格不规范的问题，但别名表目前硬编码在导入文件中。2.0 应把“字段标准、别名、类型、必填规则”收敛到一个可测试的 schema，供模板、导入、表单和 API 共同使用。

### 10.3 多规格继承规则

同一产品的多条规格应连续排列：

- 第一行填写产品组 SKU、产品名称、供应商和公共字段。
- 后续规格行可以省略产品组 SKU，并从上一组继承。
- 产品名称、供应商、链接、重量、尺寸、包装、装箱数、公开状态和备注也可以在连续规格行中继承。
- 同一产品组 SKU 不能对应多个不同产品名称。
- 同一产品组下规格 SKU 不能重复。

如果把不同产品交错排列，或者错误复用产品组 SKU，系统可能把数据合并到同一个产品组。因此模板和导入预览必须让用户看清分组结果。

### 10.4 数据写入语义

导入不是“只新增”，而是按业务键 upsert：

- 供应商按名称查找，不存在则自动创建。
- 产品组按产品组 SKU 查找，不存在则创建，存在则更新并恢复软删除状态。
- 规格按 `(产品组 ID, 规格 SKU)` upsert。
- 默认不会删除 Excel 中缺失的旧规格。
- 只有显式传入 `deleteMissing=true` 才会清理本次产品组中未出现的规格。

数据部分在一个 Prisma 事务中执行，发生行级错误时会整体回滚。事务超时设置为 120 秒。

`deleteMissing` 必须保持显式选择，因为用户可能只导入产品的部分规格；默认删除会造成不可逆的数据丢失。

### 10.5 图片来源和处理

支持三类图片来源：

- Excel 工作簿中的普通内嵌图片。
- 图片 URL 列中的 http/https 地址，多张可用逗号、分号或换行分隔。
- 前端额外传入的行号到 URL 映射。

内嵌图片按 Excel 行号落入相邻产品组区间。每个产品最多保存 12 张图片，下载单张图片超时 8 秒，整体图片处理最多 60 秒。

WPS 的 `=DISPIMG()` 是专有公式，不等同于普通图片对象或真实 URL。系统只能识别并提示，不能自动取得其中图片。

图片下载会拒绝明显的 localhost、私有 IPv4/IPv6 和链路本地地址，并限制下载大小。但当前检查只基于 URL 主机字符串，没有完整覆盖 DNS 解析后落入私网、重定向链和文件内容真实性，2.0 仍需加强 SSRF 与文件魔数校验。

### 10.6 ExcelJS 图片兼容回退

部分供应商 Excel 的 drawing anchor 结构不被 ExcelJS 正常解析，最初会被统一误报为“文件损坏”。1.0 的处理方式是：

1. 正常使用 ExcelJS 读取工作簿。
2. 如果错误明确来自 drawing/anchor，临时移除 drawing/media 关系后重试行数据。
3. 再直接读取 xlsx ZIP 中的 worksheet、drawing、relationship 和 media XML，恢复图片与行号映射。

这段 ZIP/XML 回退逻辑是为真实供应商文件兼容而存在，2.0 不能在没有回归样本的情况下简单删除。

### 10.7 导入的非原子边界

产品组和规格的数据库写入是事务性的，但图片处理在数据库事务提交之后执行，原因是避免网络下载长期占用 SQLite 写事务。

因此一次导入可能出现：

- 产品和规格导入成功。
- 部分图片下载或保存失败。
- API 返回成功，同时携带图片警告。

这不是完整的“数据库 + 文件系统”原子事务。2.0 更适合采用导入任务、临时文件、校验预览、提交阶段和可重试图片任务，而不是把所有工作塞在一个 HTTP 请求中。

## 11. Excel 导出

- 只有 admin/editor 可以导出。
- 可以按搜索条件和多个供应商筛选。
- 每个供应商生成一个工作表，工作表名会清理 Excel 非法字符并保证唯一。
- 同一产品组的公共字段会跨规格行合并。
- 表头冻结，设置列宽、行高、边框和交替底色。
- 每个产品组最多取前 4 张图片，使用 Sharp 横向合并后嵌入图片列。
- 图片从统一 `UPLOAD_DIR` 读取，而不是假定在代码仓库的 `public` 目录。
- 每个供应商最多导出 2000 个产品组。

当前达到 2000 个产品组时会直接截断，没有在文件或响应中明确提示。2.0 应提供导出任务状态、总量提示或分卷导出。

## 12. 上传与文件持久化

开发环境默认使用 `./public/uploads`，生产环境使用独立持久化目录，例如：

```text
/var/lib/supply-chain/uploads
```

公开 URL 保持 `/uploads/<净化后的SKU>/<文件名>`，由应用 Route Handler 读取实际文件。这样重新拉代码、重新构建 `.next` 或替换发布目录时不会丢图片。

文件名只保留字母、数字、下划线和连字符，其他字符替换为下划线。这个过程不是可逆映射，因此不能通过“把目录名下划线替回连字符”可靠恢复原 SKU。当前导入后的孤立文件清理包含类似推断，存在误判风险。

另外需要注意：

- 产品创建时先写文件、后写数据库；数据库创建失败可能留下孤立文件。
- 产品编辑时新文件也可能在事务失败后残留。
- 产品软删除会保留图片文件，便于未来恢复，但没有回收站清理策略。
- 供应商物理删除会删图片数据库记录，但当前没有完整删除对应物理文件。
- `/uploads` 路径当前无需登录，知道 URL 即可访问图片。若图片属于敏感资产，2.0 必须改为鉴权下载或签名 URL。

## 14. 1.0 遇到的主要问题与原因

### 14.1 局域网登录后无法跳转

**现象**：`localhost:3000` 正常，使用局域网 IP 可以打开登录页，但登录后回到登录页或周期性刷新。

**原因**：开发服务器监听地址、允许来源、Auth.js 回调地址、浏览器当前 origin 和 hydration 时机共同影响登录。只改其中一个固定 IP，换网络后还会复发。

**处理**：开发服务器监听 `0.0.0.0`；通过 `LAN_HOST` 配置允许来源；回调使用当前 origin；登录使用完整页面跳转兜底，并避免 hydration 前表单默认提交把凭据写进 URL。

**经验**：开发 LAN 地址和生产域名是两套配置。不要把临时 IP 硬编码进认证逻辑。

### 14.2 正式 HTTPS 登录成功但仍回到登录页

**现象**：认证回调 200、session 也存在，但访问首页被 307 重定向回 `/login`。

**原因**：HTTPS 生产环境使用 `__Secure-` cookie；`src/proxy.ts` 的 `getToken()` 没有声明 `secureCookie: true`，路由保护读取不到已经存在的会话。

**处理**：生产环境按 `NODE_ENV` 设置 `secureCookie`。

**经验**：登录接口成功不代表所有认证读取点都能读到同一个 cookie。Route Handler、Proxy 和 Pages Router 都要单独验证。

### 14.3 正式环境 Excel 导入提示“请先登录”

**原因**：导入接口使用 Pages Router 和独立 `getToken()`，重复出现生产安全 cookie 读取问题。

**处理**：导入接口同样根据生产环境设置 `secureCookie`。

**经验**：混用 App Router 和 Pages Router 会产生两套运行边界，认证配置必须集中封装。

### 14.4 改版 Excel 提示“没有数据”

**原因**：供应商文件把表头放在第 2 行，原解析器固定使用第 1 行作为表头。

**处理**：在前 20 行搜索三列核心表头。

**经验**：真实 Excel 往往包含标题、公司名和说明行。解析器需要识别表头，而不是假定固定行号。

### 14.5 含内嵌图片的 Excel 被误报损坏

**原因**：ExcelJS 无法解析部分 drawing anchor 结构，错误发生在图片关系而不是业务数据本身。

**处理**：增加移除 drawing 后读取行数据，以及直接解析 xlsx ZIP/XML 图片关系的回退路径。

**经验**：不能把第三方解析库的兼容错误统一翻译成“用户文件损坏”；需要保留原始错误分类和真实样本。

### 14.6 大文件上传返回 HTTP 413

**原因**：应用允许大文件，但 Nginx 仍使用较小的默认请求体限制。

**处理**：Nginx 配置 `client_max_body_size 250m`，并与 Next.js/formidable 限制协调。

**经验**：上传限制是端到端链路配置。换服务器时必须重复 Nginx 配置，代码更新不会自动带过去。

### 14.7 生产图片和导出路径失效

**原因**：早期实现假定图片始终位于仓库 `public` 目录；生产发布和重新构建可能替换该目录。

**处理**：引入统一 `UPLOAD_DIR` 和 `/uploads` Route Handler，导出也从统一路径读取。

**经验**：业务文件不能放在一次性发布目录中；数据库记录应保存稳定逻辑路径，而不是环境相关绝对路径。

### 14.8 备份脚本备份了开发数据库

**原因**：脚本没有加载 `.env`，回退到了默认 `prisma/dev.db`。

**处理**：运维脚本统一加载环境配置，并在生产检查中验证数据库路径。

**经验**：脚本、应用和 Prisma CLI 必须使用同一个环境变量加载规则。

### 14.9 不合法图片被静默跳过

**原因**：产品创建/编辑早期遇到不支持格式或超限图片时跳过图片，产品本身仍创建成功，用户误以为图片已保存。

**处理**：手工产品维护遇到坏图时返回 400；批量导入则允许数据成功并返回图片警告。

**经验**：交互式单条操作和批量任务可以采用不同失败策略，但必须明确反馈，不能静默丢数据。

### 14.10 Windows 空 SQLite 初始化异常

**现象**：特定 Windows、Node/Prisma 组合对全新空 SQLite 执行 migration 或 db push 时只返回 `Schema engine error`；现有数据库查询正常。

**结果**：正式 Linux 服务器上的空库 `prisma migrate deploy` 已验证成功。

**经验**：数据库初始化必须在目标操作系统和目标 Node 版本上做一次真实演练。项目开发和部署仍建议使用文档规定的 Node 20/22 LTS，避免把偶然可运行当成稳定兼容承诺。

## 15. 已知技术债与风险

### 15.1 2.0 前优先确认

1. **editor 供应商权限不一致**：API、页面入口、proxy 和按钮显示没有使用同一个权限来源。
2. **没有自动化回归测试**：`package.json` 有 Playwright 命令，但仓库目前没有测试目录或 Playwright 配置；当前验收主要是人工完成。
3. **导入模块过于集中**：解析、业务校验、数据库写入、XML 回退、图片下载和文件清理集中在一个约 1500 行 API 文件中。
4. **数据库与文件系统不具备联合事务**：产品和图片可能部分成功，并产生孤立文件。
5. **公开图片边界需业务确认**：`/uploads` 当前公开可访问，隐藏产品不代表图片 URL 失效。

### 15.2 中期风险

- SQLite 适合当前单机小规模场景，不适合多实例并发写入和横向扩容。
- 生产应用应保持单写实例；在 SQLite 下直接启动多个 PM2 cluster 实例风险较高。
- 产品版本号没有并发冲突检查，两个编辑者后保存的人会覆盖先保存的人。
- 供应商删除为不可恢复的级联物理删除，和产品软删除策略不一致。
- 价格、重量、尺寸等均为字符串，缺少单位规范和可计算字段。
- API 响应结构和错误码不完全统一，校验主要为手写判断。
- 公共目录无分页，导出有静默数量上限。
- 审计日志不完整，不应被当作合规级审计证据。
- 无导入历史、原文件留档、失败行报告和可重试任务。
- 无登录限流、系统级错误上报和业务指标监控。
- 本地文件存储不支持多服务器共享；迁移 OSS 前需要稳定的存储接口和数据搬迁脚本。

## 16. 2.0 重构建议

### 16.1 先冻结业务契约

重构前先把以下规则写成自动化测试和样例文件：

- 产品组和规格的唯一键及继承规则。
- editor 可以管理产品和供应商，并查看全部内部数据。
- viewer 仅查看授权供应商，且看不到供应商真名、拿货价、链接和备注。
- `isPublic` 只控制公开目录。
- 导入默认 upsert，不默认删除缺失规格。
- 软删除产品重新导入后的恢复行为。
- 普通图片、WPS `DISPIMG`、drawing anchor 异常和大文件的处理结果。

没有这些契约，重构很容易让代码更整齐但业务行为发生变化。

### 16.2 推荐模块边界

建议继续保留一个可部署单体，但在代码内拆分职责：

```text
src/
  modules/
    auth/
      policy.ts
      service.ts
    products/
      schema.ts
      repository.ts
      service.ts
    suppliers/
      schema.ts
      service.ts
    imports/
      parser.ts
      header-mapping.ts
      validator.ts
      image-extractor.ts
      import-service.ts
    exports/
      export-service.ts
    storage/
      storage.ts
      local-storage.ts
    audit/
      audit-service.ts
```

Route Handler 只负责 HTTP 输入输出；角色判断、业务校验和数据库操作放到可测试的 service/policy 中。暂时不需要拆微服务。

### 16.3 统一权限策略

建立一个角色能力表，例如 `canManageProducts`、`canManageSuppliers`、`canManageUsers`、`canViewSensitiveFields`，让以下位置共用同一份规则：

- proxy 页面保护。
- API 授权。
- 导航和按钮显示。
- 测试用例。

viewer 的供应商过滤必须在 repository/service 查询层强制附加，避免新 API 忘记过滤。

### 16.4 重做导入为任务流程

推荐流程：

1. 上传原文件到临时区并记录哈希。
2. 解析并生成标准化中间数据。
3. 返回导入预览、分组结果、错误和警告。
4. 用户确认是否覆盖、恢复软删除或删除缺失规格。
5. 在后台任务中提交数据库变更。
6. 图片单独可重试，并记录每张图片状态。
7. 保存导入历史、原文件、操作人和结果报告。

应为已遇到的每类 Excel 保存脱敏测试 fixture。XML 回退逻辑拆分后仍要保留，直到用更可靠的库完整替代并通过全部样本。

### 16.5 统一数据校验

项目已经依赖 Zod，但核心 API 仍以手写判断为主。2.0 可定义共享 schema：

- 产品表单 schema。
- 规格 schema。
- 供应商 schema。
- 用户和密码 schema。
- Excel 标准行 schema。
- API 查询参数 schema。

共享 schema 可以减少“前端允许、API 拒绝、导入又采用第三套规则”的漂移。

### 16.6 文件存储改造

先定义最小存储接口：保存、读取、删除、复制和生成访问 URL。1.0 继续使用本地实现，未来需要多机部署或 CDN 时再增加 OSS 实现。

文件写入建议采用临时文件和提交后重命名；数据库失败时清理临时文件。对删除操作增加异步回收和引用检查，避免根据净化后的目录名反推 SKU。

### 16.7 数据库升级判断

不要仅因为“2.0”就自动引入 PostgreSQL 和 Redis。满足以下任一条件时，PostgreSQL 才应进入正式迁移计划：

- 多个用户频繁同时写入。
- 导入和日常编辑开始互相阻塞。
- 需要多个应用实例或无停机发布。
- 需要更强的备份、审计、查询和运维能力。

迁移时先在预发布环境进行 SQLite 到 PostgreSQL 的全量搬迁、数量校验、外键校验和业务回归。Redis 只有在性能数据证明数据库或计算热点存在时再引入。

### 16.8 可观测性和运维

2.0 至少应补充：

- 结构化应用日志和请求 ID。
- 登录失败、导入失败、备份失败和磁盘不足告警。
- 导入耗时、成功行数、图片失败数等业务指标。
- 自动备份、异地保存和定期恢复演练。
- 发布前数据库备份、迁移、健康检查和回滚步骤。

## 17. 推荐重构顺序

1. 建立 1.0 回归测试和真实 Excel 脱敏样本库。
2. 修正并统一角色能力表，先消除 editor 权限不一致。
3. 抽离共享 schema、产品 service 和供应商 service，不改变 API 行为。
4. 拆分导入 parser、validator、image extractor 和 persistence。
5. 增加导入预览、历史、失败报告和图片重试。
6. 引入 storage 接口并解决孤立文件和受保护图片问题。
7. 根据并发与运维指标决定是否迁移 PostgreSQL。
8. 最后再做缓存、多实例和更复杂的部署拓扑。

## 18. 2.0 必备回归清单

### 认证与权限

- localhost、局域网 IP、正式 HTTPS 均能登录并稳定跳转。
- 生产安全 cookie 在 proxy、App Router 和导入接口中均可读取。
- 连续 5 次失败锁定，管理员重置密码后解除。
- admin、editor、viewer 的页面、API 和字段权限一致。
- viewer 空授权时看不到任何内部产品。

### 产品与供应商

- 产品组、多规格、多图片新增和编辑。
- 规格新增、修改、删除及跨产品规格 ID 拒绝。
- 产品软删除及重新导入恢复。
- 供应商重名拒绝和删除影响确认。
- 12 张图片边界、10 MB 边界和非法格式拒绝。

### 导入导出

- 标准模板、表头第 2 行、别名表头和多规格留空继承。

- 普通内嵌图片、多个图片 URL、WPS `DISPIMG` 提示。
- drawing anchor 异常文件和 76 MB 级大文件。
- 默认保留 Excel 中未出现的规格；显式选择后才删除。
- 导出多供应商、多规格、图片和生产持久化路径。

### 运维

- 全新空库应用 migration。
- 生产检查 0 failed、0 warnings。
- 数据库和 uploads 一起备份与恢复。
- 服务器重启后 PM2 自动恢复。
- 发布后数据库、图片、登录和导入仍正常。

## 19. 当前结论

1.0 已经可以在当前单服务器、小团队规模下正式使用，其最有价值的资产不是页面样式，而是经过真实供应商文件验证的产品组模型、权限规则、Excel 兼容逻辑、生产认证修复和部署运维经验。

2.0 重构应优先保护这些已经验证的业务行为，再改善模块边界、自动化测试、导入任务化、文件一致性和运维能力。不要直接照搬旧的 v2 架构草案，也不要在缺少指标时提前引入微服务、Redis 或多实例复杂度。
